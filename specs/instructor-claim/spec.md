# Feature Specification: 대리 등록 강사의 계정 연결 (클레임)

## Overview

운영자가 대신 등록해 둔 강사가 강사 신청에서 같은 인스타 계정을 넣으면 가져오기를 신청하고, 인스타 DM으로 받은 코드를 넣으면 그 프로필과 클래스가 자기 계정으로 넘어와 바로 승인된 강사가 된다(F-19, 05 플로우 9).

## User Scenarios & Testing (mandatory)

### User Story 1: 강사가 대리 프로필을 가져온다

- As: 운영자가 대신 등록해 둔 강사는
- I: 내 인스타 계정으로 본인 확인을 하고 그 프로필과 클래스를 내 계정으로 가져올 수 있다
- So: 내 클래스를 직접 고치고 새로 올리기 위해

#### Acceptance Scenarios

Scenario 1: **가져오기 제안**

- Given: 클래스 2개가 있는 미연결 대리 강사 @minji.dance가 있을 때
- When: 강사 프로필이 없는 사용자가 강사 신청에 @minji.dance를 넣으면
- Then: 막히는 대신 "이미 올빗에 등록된 클래스가 2개 있어요. 내 계정으로 가져올까요?"와, 가져오면 숨어 있던 클래스가 공개된다는 안내를 본다

Scenario 2: **가져오기 신청**

- Given: 가져오기 제안에서
- When: 가져오기를 신청하면
- Then: 신청 화면이 "인스타 본인 확인을 기다리는 중"이 되고 코드를 넣는 칸이 보인다. 마이에도 가져오기 중이라고 보인다

Scenario 3: **코드 확인 → 이전**

- Given: 운영자가 코드를 발급해 DM으로 보냈을 때
- When: 강사가 맞는 코드를 24시간 안에 넣으면
- Then: 그 프로필이 강사 계정에 연결되고 승인된 강사가 된다. 내 클래스에 원래 클래스 2개가 보이고 고칠 수 있다

Scenario 4: **동의 없던 클래스 공개**

- Given: 게재 동의가 없어 숨어 있던 대리 강사의 다가오는 클래스와, 그 곡에 기다리는 추가요가 있을 때
- When: 가져오기가 끝나면
- Then: 클래스가 수강생에게 공개되고 그 추가요가 "열렸어요"가 된다

Scenario 5: **틀린 코드·만료·미발급**

- Given: 가져오기 신청 상태에서
- When: 틀린 코드, 24시간 지난 코드를 넣거나, 아직 발급 전에 넣으면
- Then: 각각 그렇다고 알리고 아무것도 넘어가지 않는다

Scenario 6: **신청 취소**

- Given: 가져오기 신청 상태에서
- When: 강사가 신청을 취소하면
- Then: 다시 강사 신청 화면으로 돌아가고 대리 강사는 그대로다

Scenario 7: **다른 사람이 다시 신청**

- Given: A가 가져오기를 신청하고 코드가 발급된 뒤
- When: B가 같은 대리 강사에 가져오기를 신청하면
- Then: A의 신청과 코드는 무효가 되고, A가 그 코드를 넣어도 넘어가지 않는다

Scenario 8: **신청할 수 없는 경우**

- Given: 이미 강사 프로필(대기·확인됨·승인)이 있는 사용자, 또는 이미 다른 계정에 연결된 강사의 핸들일 때
- When: 가져오기를 신청하면
- Then: 그렇다고 알리고 신청되지 않는다

Scenario 9: **반려됐던 사용자**

- Given: 강사 신청이 반려된 사용자가
- When: 대리 강사를 가져오기 신청하고 코드를 확인하면
- Then: 반려된 신청은 사라지고 대리 프로필이 그 사람의 강사 프로필이 된다

### User Story 2: 운영자가 가져오기를 돕는다

#### Acceptance Scenarios

Scenario 10: **신청 보기·코드 발급**

- Given: 가져오기 신청이 들어왔을 때
- When: 운영 화면을 열면
- Then: 신청 건수가 눈에 띄고, 그 대리 강사 화면에서 누가 언제 신청했는지 보고 코드를 발급(다시 발급)할 수 있다

Scenario 11: **운영자 취소**

- Given: 가져오기 신청이 있는 대리 강사에서
- When: 운영자가 신청을 취소하면
- Then: 신청과 코드가 지워지고, 강사 화면은 다시 신청 전 상태가 된다

## Functional Requirements (mandatory)

- FR-1: MUST 강사 신청에서 핸들이 미연결 대리 강사와 같으면 오류 대신 가져오기 제안(클래스 수, 공개 안내)을 돌려준다. 연결된 강사의 핸들이면 지금처럼 막는다
- FR-2: MUST 가져오기 신청은 로그인·약관 동의한 사용자 중 강사 프로필이 없거나 반려된 사람만 할 수 있다. 한 사람은 한 번에 한 대리 강사만 신청한다
- FR-3: MUST 같은 대리 강사에 새 신청이 오면 앞 신청과 코드를 지운다
- FR-4: MUST 코드 확인 전에는 대리 강사의 소유와 공개 상태가 바뀌지 않는다
- FR-5: MUST 맞는 코드(본인 신청, 24시간 안)를 넣으면 한 처리 안에서 프로필을 그 사용자에 연결하고 직접 강사로 바꾸며, 반려된 내 프로필이 있으면 지운다. 상태는 승인이다
- FR-6: MUST 이전으로 새로 공개되는 다가오는 클래스의 곡들의 대기 추가요를 연다
- FR-7: MUST 강사는 가져오기 신청을 취소할 수 있다
- FR-8: MUST 운영자는 가져오기 신청이 있는 대리 강사에 코드를 발급하고 신청을 취소할 수 있다. 운영 홈에 신청 건수가 보인다
- FR-9: MUST 마이와 신청 화면이 가져오기 진행 상태를 보여준다

## Constraints (mandatory)

- CON-1: MUST 코드 원문은 저장하지 않는다(기존 방식)
- CON-2: MUST 걸리는 시간이나 자동 DM을 약속하지 않는다(원칙 6)
- CON-3: MUST 코드 없는 운영자 직접 연결, 이전 되돌리기, 알림은 이번에 없다
- CON-4: MUST 수강생·강사 화면은 design.md, 운영 화면은 단순 표·다크 규칙

## Success Criteria (mandatory)

- SC-1: 되돌리는 트랜잭션 테스트에서 시나리오 1~9, 11의 데이터 변화가 기대와 같다
- SC-2: 마이그레이션 뒤 `pnpm db:generate`가 "No schema changes"이고 `pnpm check`가 통과한다
