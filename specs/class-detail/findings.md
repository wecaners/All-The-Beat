- F-05 예약 버튼 위 안내: "예약은 강사님의 OO에서 진행돼요"
- F-05 상태별: 모집중·마감 임박 → 예약 가능 / 마감·종료 → (앵콜) + 같은 곡 다른 클래스 / 취소 → 비활성 + 같은 곡 다른 클래스 + 이 곡 추가요
- F-06: `/go/{classId}`를 거쳐 클릭 1건 기록 후 외부로. 기록 항목은 클래스 ID·시각·로그인 사용자 ID(있으면)·유입 경로. 같은 사용자(또는 브라우저)·같은 클래스는 10분 안 중복이면 1회. 외부 링크는 새 탭
- 04 IA: `/class/{id}`는 OG 태그 필수, 탭바 없음, 외부에서 바로 들어와도 홈으로 가는 길(로고)이 있어야 한다
- 08 아키텍처: `/go` 리다이렉트 대상은 DB에 저장된 그 클래스의 링크뿐 (오픈 리다이렉트 방지). 이벤트 로그에 IP는 저장하지 않고 세션 ID(쿠키)만
- MVP 원칙 6: 앵콜(F-24)이 없으므로 마감·종료 화면에서 앵콜을 약속하지 않는다

## Research Findings

### 코드베이스 구조

- 클래스 라우트는 아직 없다. 곡 상세의 티켓이 이미 `/class/{id}`로 링크하고 있어 지금 누르면 404다
- `classes` 테이블에 F-05 항목이 모두 있다(제목·일시·장소 스냅샷·권역·가격·난이도·정원·예약 링크·예약 유형·썸네일 경로·설명·상태·숨김). 곡은 `class_songs`(position 1~3, 1이 대표)
- 클릭 기록용 `events` 테이블이 있다: `type`(`booking_click` 등), `class_id`, `user_id`, `session_id`(NOT NULL), `referrer`, 인덱스 `(type, class_id, created_at)`. **스키마 변경이 필요 없다**
- `class_status`는 `open·closing_soon·closed·ended·canceled`. 문서상 "종료 시각이 지나면 자동 종료"는 하루 1회 배치(`/api/cron/daily`)의 일인데, 배치는 아직 없다. DB의 상태는 시각이 지나도 `open`으로 남는다
- `thumbnailPath`를 채우는 곳이 없다(운영자 등록 폼에 이미지 업로드 없음). 지금은 모든 클래스가 곡 영상 썸네일로 대체된다
- 세션 ID 쿠키(비로그인 중복 제거용)는 아직 없다. 지금 쿠키는 Supabase 로그인 쿠키뿐

### 기존 패턴

- 공개 조건 `publiclyVisible`(숨김 아님 + 승인된 강사 + 대리 등록이면 게재 동의): `app/src/server/classes/index.ts` — 상세도 같은 조건을 써야 곡 상세와 어긋나지 않는다
- 곡 상세: 곡 정보는 `"use cache"` + `cacheTag`, 요청마다 다른 데이터는 `<Suspense>` 안에서 `await connection()` 뒤. 한글 slug는 `readSlug`로 디코드
- `generateMetadata`로 제목·설명·OG를 만든다 (OG 이미지는 아직 없음)
- 추가요 시트는 `?request=open`으로 자동으로 열린다 (로그인 복귀용으로 이미 있음) → 취소된 클래스의 "이 곡 추가요"가 그대로 쓸 수 있다
- 예약 유형은 운영자 등록 때 URL로 추정한다(`guessBookingType`)
- 화면 부품: `StickerButton`(`ink` 변형 = 밖으로 나가는 버튼), `InfoChip`, `StickerLabel`, `VideoCard`, `ClassTicket` (`_agent/rules/design.md`)

## Technical Decisions

| Decision | Rationale |
| -------- | --------- |
| 종료 여부는 저장된 상태가 아니라 종료 시각으로 판단한다 (취소가 우선) | 자동 종료 배치가 아직 없어 DB 상태가 `open`으로 남는다. 끝난 클래스로 예약을 보내면 안 된다. 배치가 생겨도 같은 결과라 바꿀 필요가 없다 |
| 상세·`/go` 모두 곡 상세와 같은 공개 조건을 쓰고, 공개되지 않은 클래스는 없는 것처럼 404 | 동의 없는 대리 등록 클래스가 링크 추측(`/class/1`, `/class/2`…)으로 드러나면 안 된다 (F-15) |
| `/go`는 Route Handler(GET)로, DB의 `booking_url`로만 302 | 08 문서의 오픈 리다이렉트 방지. 링크는 `<a>`라 새 탭 열기·길게 눌러 복사가 자연스럽다 |
| 예약할 수 없는 상태(마감·종료·취소)에서 `/go`로 들어오면 기록하지 않고 클래스 상세로 돌려보낸다 | 화면 버튼은 막았어도 옛 링크·공유 주소로 들어올 수 있다. 마감된 클래스의 예약 채널로 보내면 수강생이 헛걸음한다 |
| 클릭 중복 제거: 로그인하면 사용자 ID, 아니면 세션 쿠키 기준으로 같은 클래스 10분 안이면 저장하지 않는다. 한 문장(`INSERT … WHERE NOT EXISTS`)으로 처리 | 10분 창은 유니크 제약으로 표현할 수 없다(`app.md`의 "유니크 + upsert" 원칙의 예외). 동시에 두 번 눌러 2건이 되는 경합은 지표 오차로 받아들인다 |
| 세션 쿠키는 `/go`에서 없을 때만 무작위 값으로 만든다 (httpOnly) | 기록할 때만 필요하다. 클래스 상세를 보기만 한 사람에게는 쿠키를 굽지 않는다 |
| 이번에는 `booking_click`만 기록하고, 조회 수(`class_view`)는 기록하지 않는다 | README 범위. 조회 기록은 F-18 지표 화면과 함께 정한다 |
| 화면 데이터는 요청마다 읽는다 (캐시 안 함) | 종료 여부가 지금 시각에 달려 있고, 상태(마감 임박·마감)가 자주 바뀐다. 클래스 한 건 조회라 부담이 작다 |
| 지도는 네이버 지도 주소 검색으로 연다 | 장소는 주소 문자열만 있고 좌표가 없다. 네이버 지도가 앱이 있으면 앱으로, 없으면 웹으로 열린다 |
| 썸네일: 클래스 이미지 → 대표 곡(position 1)의 영상 썸네일(YouTube 표시) → 없으면 이미지 없이 | F-05와 06 문서 4.1. 지금은 클래스 이미지를 올리는 곳이 없어 사실상 곡 썸네일이다 |
| 마감·종료 화면에 앵콜을 두지 않는다 | MVP 원칙 6. F-24를 만들 때 이 자리에 넣는다 |
| 예약하러 가기는 `next/link`가 아니라 일반 `<a target="_blank">`로 건다 | `next/link`는 화면에 보이면 미리 불러오기로 `/go`를 호출해 누르지 않은 클릭이 기록된다 |
| URL의 클래스 번호는 숫자만 받는다 (`^[1-9][0-9]{0,14}$`) | `0x10`, `1e3` 같은 다른 표기로 같은 클래스가 열리지 않게 한다 |
| 클래스 상세 화면을 데이터만 받는 `ClassView`(`app/src/app/class/[id]/class-view.tsx`)로 분리 | 마감·종료·취소 화면을 DB를 바꾸지 않고 가짜 데이터로 확인하기 위해. 운영과 같은 DB라 상태를 바꿔 볼 수 없다 |
| `thumbnailPath`는 아직 화면에 쓰지 않는다 | 채우는 곳이 없고 Storage 공개 주소 규칙도 정하지 않았다. 클래스 이미지 올리기를 만들 때 붙인다 |
| 강사·장소를 정보 표에서 빼 섹션을 따로 둔다 (1단계, 데이터 변경 없음) | 사용자 제안: 강사는 자기를 알리고 싶고, 수강생은 연습실 위치·컨디션을 중요하게 본다. 인스타로 나가면 예약 전에 이탈하기 쉬워 핵심은 올빗 안에 둔다 |
| 장소는 지도 임베드 대신 "네이버 지도"(앱 열기) + "주소 복사" | 03 명세 8절이 지도 보기를 MVP에서 뺐다. 모바일에서는 지도 앱이 길 찾기에 낫다 |
| 지도는 카카오맵으로 통일한다 (열기 링크 `map.kakao.com/link/search/{주소}`, 앞으로의 지도 미리보기·주소→좌표도 카카오) | 사용자 결정(2026-10-28). 로그인용 카카오 앱이 이미 있어 새 서비스 가입 없이 카카오맵·로컬 API를 켤 수 있다. 네이버 지도 API(NCP)는 새 가입과 대표 계정 조건이 필요하다 |
| 강사 사진 자리는 이름 첫 글자 동그라미 | 사진을 아직 받지 않는다. 남의 사진처럼 보이는 가짜 이미지를 두지 않는다 |

### 2. 유입 경로(referrer)가 늘 우리 클래스 페이지가 된다

**문제**:

`/go`는 클래스 상세에서 누르므로 요청의 referrer는 항상 `/class/{id}`다. F-06이 원한 "인스타에서 왔는지, 곡 상세에서 왔는지"는 이 값으로 알 수 없다.

**원인**:

진짜 유입 경로는 클래스 상세를 처음 연 순간의 referrer다.

**해결**:

이번에는 `/go` 요청의 referrer를 그대로 저장한다. 바깥 유입 경로는 조회 기록(`class_view`)과 함께 F-18에서 다룬다.

**결과**:

### 3. 없는 클래스의 404가 HTTP 200으로 나갈 수 있다

### 5. 예약 이동 실제 기록은 확인하지 않았다

**문제**:

`/go/1`(공개 모집 중 테스트 클래스)로 실제 이동하면 `events`에 1건이 남는다. dev DB가 운영 배포와 같은 DB라 사용자 확인 없이 쓰지 않았다.

**원인**:

운영 DB 분리 전이다 (`_agent/handoff.md` 출시 전 할 일).

**해결**:

같은 SQL을 트랜잭션 안에서 돌리고 되돌려 중복 제거를 확인했다 (같은 세션 2번 → 1, 다른 세션 → 1, 11분 뒤 → +1, 로그인 사용자 두 브라우저 → 1, 되돌린 뒤 events 0건). 404 경로(`/go/999999`, `/go/abc`, `/go/0x1`)는 기록 없이 확인했다.
사용자 승인 후 `/go/1`을 실제로 열었다: 첫 요청 302(구글 폼) + `ab_sid` 쿠키(HttpOnly, SameSite=lax, 1년) + `booking_click` 1건(비로그인, referrer `/class/1`). 같은 쿠키로 다시 열면 302만 되고 쿠키를 다시 굽지 않으며 기록은 늘지 않았다. 확인용 기록 1건은 공용 DB에 남아 있다.

**결과**:

해결

**해결**:

2단계(강사 사진·한 줄 소개·포트폴리오 YouTube 1~2개, 장소 시설 태그)는 스펙을 따로 쓴다. 스키마·사진 저장소·운영자 입력·대리 등록 동의 범위 확대가 필요하다. 3단계(장소 사진 목록·크게 보기, 지도 미리보기)는 그 뒤에. 지도 미리보기는 03 명세 8절을 바꿔야 한다. 인스타 자동 연동은 Graph API가 비즈니스 계정과 Meta 앱 심사를 요구해 하지 않는다.
지도는 카카오로 정했다(사용자가 카카오 디벨로퍼스에서 카카오맵 사용 설정). 장소는 "강사의 스튜디오"로 다룬다: 클래스 등록 때 내 스튜디오를 고르고, 좌표·사진·시설은 스튜디오에 붙인다(`instructor_places` 확장).

## Learnings

### 잴 수 있는 끝까지가 서비스의 성공이다 (2026-10-28)

예약을 외부에 맡기면 실제 예약 성사는 알 수 없다. 대신 "예약 채널로 넘어간 순간"을 정확히 세는 것이 강사에게 보여줄 유일한 숫자이자 서비스가 일하는지 판단할 근거가 된다. 그래서 `/go`는 단순 리다이렉트가 아니라 지표의 입구로 다룬다.

### 스펙 리뷰는 사용자가 생략할 수 있다 (2026-10-28)

사용자가 README·spec까지 보고 "리뷰는 스킵하고 끝까지 진행"을 지시했다. plan 이후는 리뷰 없이 쓰고 바로 구현한다. 리뷰를 건너뛴 만큼 결정은 이 파일에 빠짐없이 남겨, 나중에 사용자가 한 곳에서 확인할 수 있게 한다.
