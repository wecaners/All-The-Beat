## Research Findings

### 코드베이스 구조

- 곡 제목과 아티스트 대표 이름도 별칭 테이블에 `is_primary` 행으로 들어간다(`addAliases`). 그래서 검색은 `song_aliases`·`artist_aliases` 두 테이블만 보면 된다
- 정규화 `normalizeAlias`(`app/src/lib/normalize.ts`): NFKC → 소문자 → 글자·숫자만. 결과에는 `%`·`_`가 남지 않아 LIKE 패턴에 그대로 넣어도 안전하다
- 두 별칭 테이블의 `alias_norm`에 trigram GIN 인덱스가 있다(`pg_trgm`, `extensions` 스키마)
- 운영자 클래스 등록 폼은 전체 곡 드롭다운 3개(`listSongOptions`)를 쓴다
- 홈에는 검색 입구가 없다(검색 화면이 없어서 보류했었다, specs/home)
- 곡 상세의 기다리는 수는 최근 90일·취소 제외(`getRequestSummary`)

### 기존 패턴

- 요청마다 다른 결과는 `<Suspense>` 안에서 `searchParams`를 읽는다
- 공개 클래스 조건 `publiclyVisible`, 영상 표시 규칙 `visibleVideoId`
- 운영 서버 액션은 첫 줄 `requireAdmin()`

## Technical Decisions

| Decision | Rationale |
| -------- | --------- |
| 검색은 정규화한 검색어를 곡 별칭·아티스트 별칭의 `alias_norm`에 포함(LIKE) 검색 | 제목·대표 이름도 별칭 행이라 두 테이블로 끝난다. trigram 인덱스가 포함 검색을 받친다(3글자 미만은 순차 검색이지만 지금 규모에서 충분) |
| 순위: 곡 별칭 정확 일치 > 아티스트 별칭 정확 > 곡 별칭 앞부분 > 아티스트 앞부분 > 곡 포함 > 아티스트 포함, 같으면 다가오는 클래스 수 → 기다리는 수 → 곡명 | 곡이 주인공(원칙 1). 아티스트 이름을 치면 그 아티스트 곡 전체가 나오되, 곡 이름이 정확히 맞는 곡이 맨 위 |
| 결과는 최대 20곡, 병합된 곡·병합된 아티스트 제외 | 화면 한 번에 볼 만큼. 병합된 곡은 대상 곡으로 나온다 |
| 검색어는 주소(`?q=`)로 두고, 치는 동안 0.25초 쉬면 주소를 바꿔(`router.replace`) 서버가 결과를 그린다 | 새로 고침·공유·곡 상세에서 뒤로 왔을 때 같은 결과. 결과 계산은 서버(브라우저는 DB에 안 감) |
| 결과 목록에는 등장 애니메이션(착착 붙기)을 쓰지 않는다 | 칠 때마다 다시 그려져 매번 움직이면 읽기 어렵다 (design.md 인터랙션 표에 남긴다) |
| 기다리는 수는 곡 상세와 같은 최근 90일·취소 제외 | 같은 곡의 숫자가 화면마다 다르면 혼란 |
| 운영자 곡 고르기는 같은 `searchSongs`를 서버 액션으로 부른다. 기본 한 칸, "다른 곡도 배워요"로 최대 세 칸 | 수강생 검색과 같은 규칙(F-13). 대부분 한 곡 |
| 검색 결과 행은 공용 부품 `SongRow`로 | 추가요 랭킹(F-08)·마이(F-10)에서도 곡 한 줄을 같은 모양으로 쓴다 |
| 검색 칸은 서버에서 검색어를 받지 않고 미리 그려진 화면에 바로 둔다. 검색어는 브라우저에서 주소를 읽는다(`useSyncExternalStore`, 서버 값은 빈 칸) | 처음엔 `<Suspense>` 안에서 검색어를 받아 그렸는데, 불러오는 동안 대체 칸이 진짜 칸으로 바뀌면서 열자마자 친 글자가 사라질 수 있었다 |
| 곡 고르기에서 찾는 곡이 없으면 곡명·아티스트만으로 그 자리에서 만든다(F-13 일부). 같은 아티스트(다른 이름 포함)에 같은 곡명(다른 이름 포함)이 있으면 새로 만들지 않고 그 곡을 고른다 | 사용자 지적: 새 곡마다 곡 등록 화면을 따로 거치면 클래스 등록이 막힌다. 곡은 한 번 만들면 모든 클래스가 같이 쓴다. 별칭·영상은 나중에 곡 화면에서 |

## Issues Encountered

### 1. 결과 없음에서 추가요로 바로 가지 못한다

**문제**:

F-02 수용 기준 "결과 없음에서 두 번 안에 추가요"는 없는 곡을 만드는 기능(F-13)이 있어야 지킬 수 있다.

**원인**:

추가요는 곡에 붙는다. 없는 곡에는 남길 곳이 없다.

**해결**:

이번에는 "아직 올빗에 없는 곡"이라고 알리고 다른 표기로 다시 쳐 보게 한다(원칙 6). F-13에서 결과 없음 → 곡 만들기 → 추가요를 잇는다.

**결과**:

보류

### 2. 곡이 없으면 클래스 등록이 막힌다

**문제**:

운영자는 클래스에 붙일 곡이 없으면 곡 등록 화면에서 곡을 먼저 만들어야 한다. 곡은 한 번 만들면 모든 클래스가 같이 쓰지만, 새 곡이 나올 때마다 따로 등록하는 수고가 있다(사용자 지적).

**원인**:

곡을 만드는 길이 운영자 곡 등록 화면 하나뿐이다. F-13(검색 결과 없음 → 그 자리에서 새 곡)은 아직 없다.

**해결**:

사용자 결정(2026-10-28): 곡 고르기에서 바로 새 곡 만들기. 곡명·아티스트만 받고, 기존 아티스트는 다른 이름으로 쳐도 묶이며, 같은 곡이 있으면 그 곡을 고른다(중복 확인 쿼리를 읽기 전용으로 확인). 수강생 검색의 "결과 없음 → 추가요"(사용자가 곡을 만드는 F-13)는 여전히 남는다.

**결과**:

해결 (운영자 곡 고르기). 실제 생성은 운영자 로그인으로 사용자 확인

## Learnings

### 같은 검색을 수강생과 운영자가 같이 쓴다 (2026-10-28)

곡 고르기 드롭다운은 곡이 몇 개일 때만 동작하는 임시 방법이었다. 수강생 검색을 만들 때 운영자 곡 고르기도 같은 검색으로 바꾸면 규칙이 한 곳에 모이고, 나중에 강사가 직접 등록할 때도 그대로 쓴다.
