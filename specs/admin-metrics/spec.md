# Feature Specification: 운영자 지표

## Overview

운영자가 운영 첫 화면에서 기획서 6절의 성공 지표 7개를 목표와 나란히 보고, 서비스가 일하고 있는지 판단한다(F-18, A-06). 재방문을 세기 위해 로그인 사용자가 들어온 날짜를 하루 한 번 남기기 시작한다.

## User Scenarios & Testing (mandatory)

### User Story 1: 운영자가 지표를 본다

- As: 운영자는
- I: 운영 화면에 들어가자마자 성공 지표를 목표와 함께 볼 수 있다
- So: DB를 뒤지지 않고 매주 다음 단계로 갈지 판단하기 위해

#### Acceptance Scenarios

Scenario 1: **첫 화면**

- Given: 운영자로 로그인했을 때
- When: 운영 화면에 들어가면
- Then: 지표 7개가 먼저 보이고, 지금 있던 할 일 목록(검수 대기 곡, 앵콜 응답 대기, 다가오는 클래스, 강사, 곡)은 그 아래에 그대로 있다

Scenario 2: **목표와 함께**

- Given: 목표가 있는 지표(클래스 30, 자발적 강사 3, 예약 클릭 50, 요청 → 개설 1곡, 재방문 10명)에서
- When: 지표를 보면
- Then: 지금 값과 목표가 같이 보이고, 목표에 닿았는지 알 수 있다

Scenario 3: **등록된 클래스 수**

- Given: 운영자 대리 등록 클래스 2개(하나는 이번 주), 강사 직접 등록 클래스 1개, 취소된 클래스 1개, 숨긴 클래스 1개가 있을 때
- When: 지표를 보면
- Then: 누적 3(대리 2, 직접 1), 이번 주 1로 보인다. 취소·숨김은 빠진다

Scenario 4: **자발적 등록 강사 수**

- Given: 강사 A가 직접 올린 클래스 2개, 강사 B가 직접 올렸다가 취소한 클래스 1개, 강사 C는 대리 등록 클래스만 있을 때
- When: 지표를 보면
- Then: 2명(A, B)으로 보인다

Scenario 5: **예약 링크 클릭**

- Given: 여러 클래스에 예약 클릭이 쌓여 있을 때(숨긴 클래스 포함)
- When: 지표를 보면
- Then: 누적과 이번 주 클릭 수가 보이고, 클릭이 많은 클래스 순으로 클래스와 클릭 수가 보인다. 숨긴 클래스의 클릭도 들어간다. 클래스를 누르면 운영 클래스 상세로 간다

Scenario 6: **추가요 수**

- Given: 대기 중 추가요 3건, 열렸어요 추가요 1건, 취소된 추가요 2건이 있을 때
- When: 지표를 보면
- Then: 누적 4건으로 보이고, 추가요가 많은 곡 순으로 곡과 건수가 보인다. 곡을 누르면 운영 곡 화면으로 간다

Scenario 7: **요청 → 개설 전환**

- Given: 추가요가 있던 곡에 클래스가 공개되어 그 추가요가 열렸어요가 된 적이 있을 때
- When: 지표를 보면
- Then: 그런 곡 수와 곡 목록이 보인다. 그 뒤 수강생이 추가요를 취소했어도 전환된 곡으로 남는다

Scenario 8: **앵콜 → 개설 전환**

- Given: 앵콜 기준 인원을 넘은 클래스 4개 중 1개의 앵콜 클래스가 열렸을 때
- When: 지표를 보면
- Then: 1 / 4가 보인다. 기준을 넘은 클래스가 없으면 비율 대신 아직 없다고 보인다

### User Story 2: 재방문을 센다

- As: 운영자는
- I: 가입한 사람 중 2주 안에 다시 온 사람 수를 볼 수 있다
- So: 신곡 주기로 돌아오는 사람이 있는지 알기 위해

#### Acceptance Scenarios

Scenario 9: **접속 날짜 기록**

- Given: 로그인한 사용자가
- When: 같은 날 여러 화면을 여러 번 열면
- Then: 그 사용자의 그날 접속은 한 번만 남는다. 다음 날 다시 열면 그날이 한 번 더 남는다. 비로그인 방문은 남지 않는다

Scenario 10: **기록이 실패해도**

- Given: 접속 기록을 남기지 못하는 상황(DB 오류 등)에서
- When: 로그인 사용자가 화면을 열면
- Then: 화면은 평소처럼 열린다

Scenario 11: **재방문 수**

- Given: 기록 시작 뒤 가입한 사람 중 D는 가입 다음 날 다시 왔고, E는 가입한 날 여러 번만 왔고, F는 가입 20일 뒤에 처음 다시 왔을 때
- When: 지표를 보면
- Then: 재방문 1명(D)으로 보이고, 함께 센 가입자 수(3명)와 기록을 시작한 날이 보인다. 기록 시작 전 가입자, 운영자, 탈퇴한 사람은 세지 않는다

### User Story 3: 운영자만 본다

#### Acceptance Scenarios

Scenario 12: **권한**

- Given: 운영자가 아닌 사용자나 비로그인 방문자가
- When: 운영 화면 주소를 열면
- Then: 지금처럼 들어갈 수 없다

## Functional Requirements (mandatory)

- FR-1: MUST 운영 첫 화면 맨 위에 지표 7개를 보여주고, 기존 할 일 목록은 아래에 그대로 둔다
- FR-2: MUST 목표가 있는 지표 5개는 지금 값·목표·도달 여부를 같이 보여준다
- FR-3: MUST 등록된 클래스 수는 취소·숨김을 빼고 누적과 이번 주(KST 월요일 0시부터 올린 것)를, 대리 등록과 강사 직접 등록으로 나눠 보여준다
- FR-4: MUST 자발적 등록 강사 수는 직접 올린 클래스가 하나라도 있는 강사 수다(클래스 상태 무관)
- FR-5: MUST 예약 링크 클릭은 모든 클래스(숨김·취소 포함)의 누적·이번 주와, 클릭 많은 클래스 순 목록(최대 10개)을 보여준다
- FR-6: MUST 추가요 수는 취소되지 않은 추가요의 누적과, 많은 곡 순 목록(최대 10개)을 보여준다
- FR-7: MUST 요청 → 개설 전환은 클래스 공개로 추가요가 열렸어요가 된 적이 있는 곡 수와 그 곡 목록을 보여준다
- FR-8: MUST 앵콜 → 개설 전환은 기준 인원에 닿은 클래스 수 중 앵콜 클래스가 열린 수를 보여준다
- FR-9: MUST 로그인 사용자의 접속을 사용자 × 날짜(KST) 1건으로 남긴다. 하루에 여러 번 와도 1건이다
- FR-10: MUST 재방문은 기록 시작일 이후 가입한 사람(운영자·탈퇴자 제외) 중, 가입한 날 다음 날부터 14일 안에 접속한 날이 있는 사람 수다. 함께 센 가입자 수와 기록 시작일을 보여준다
- FR-11: MUST 목록의 항목은 해당 운영 화면(클래스 상세, 곡)으로 이어진다
- FR-12: MUST 숫자는 화면을 열 때마다 새로 센다

## Constraints (mandatory)

- CON-1: MUST 운영자만 본다. 수강생·강사 화면은 바뀌지 않는다
- CON-2: MUST 지표 때문에 따로 저장하는 숫자(집계 값)를 두지 않는다. 새로 남기는 것은 접속 날짜뿐이다
- CON-3: MUST 접속 기록에는 사용자와 날짜만 남긴다. IP·기기·방문한 주소는 남기지 않는다
- CON-4: MUST 접속 기록이 실패해도 사용자의 화면은 막히지 않는다
- CON-5: MUST 접속 기록이 모든 요청마다 DB에 쓰지 않는다. 같은 브라우저에서는 하루 한 번만 시도한다
- CON-6: MUST 차트, 기간 고르기, 내려받기, 조회 수·검색어·유입 경로는 이번에 없다
- CON-7: MUST 운영 화면 규칙(단순 표·다크)

## Success Criteria (mandatory)

- SC-1: 되돌리는 트랜잭션 테스트에서 시나리오 3~8의 데이터를 넣으면 각 지표가 기대한 값을 준다
- SC-2: 같은 사용자의 같은 날 접속을 여러 번 기록해도 1건이고, 다음 날은 1건이 더 생긴다
- SC-3: 시나리오 11의 데이터로 재방문 1명, 가입자 3명이 나온다
- SC-4: 접속 기록이 실패하도록 만들어도 로그인 사용자의 화면이 열린다
- SC-5: `pnpm check`가 통과하고, 개발 서버 로그에 "unstable value … while prerendering"이 없다
