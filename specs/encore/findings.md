## Requirements

- F-24: 마감 또는 종료 후 30일 이내 클래스에서 앵콜. 로그인 필요(추가요와 같은 복귀 흐름), 사용자 × 클래스 = 1건, 희망 시간대·한마디(100자) 선택
- 기준 인원: 정원의 30%(최소 3명), 정원 없으면 5명. 종료 후 30일이 지나면 만료
- 상태: 모으는 중 → 전달됨(기준 도달) → 검토 중(강사 응답) → 앵콜 오픈 / 이번엔 어려워요, 모으는 중·전달됨에서 30일 지나면 만료 (05 S-4)
- 상태는 뒤로 가지 않는다. 취소는 어느 상태에서든 막지 않는다. 수강생 화면 인원은 항상 실제 현재 인원
- "검토 중"은 강사가 응답했을 때만. 우선 예약 같은 보장 못 하는 혜택 문구 금지
- 강사 쪽: 인원(검토 시작 시점·지금 두 숫자), 희망 시간대 분포, 한마디 최근 5개, 기대치 안내 고정 문구, 응답 버튼 3개. MVP는 운영자가 DM으로 전달
- 앵콜 클래스: F-12 복사해서 만들기(곡·장소·가격·링크 복사, 날짜만), 원 클래스와 연결, 새 클래스에 앵콜 배지와 원 클래스 링크, 원 클래스에 "앵콜 클래스가 열렸어요" 배너
- 수용 기준 6개 (`docs/03-기능명세서.md` F-24)

## Research Findings

### 코드베이스 구조

- 스키마가 이미 있다: `encores`(사용자 × 클래스 UK, `canceled_at`, 한마디 100자 CHECK, 유효 앵콜 부분 인덱스), `encore_rounds`(클래스당 1행, `threshold`·`status`·`reached_at`·`reviewing_at`·`count_at_review`·`responded_at`·`encore_class_id` UK·`expires_at`), `classes.encore_of_class_id`. 마이그레이션이 필요 없다
- 클래스 표시 상태는 `displayStatusOf(status, ended)`로 정한다. 종료는 DB 시각으로 비교(`classEnded`)
- 공개 조건 `publiclyVisible`(숨김 아님·승인 강사·대리면 게재 동의)은 `instructor_profiles`를 join한 쿼리에서만 쓴다
- 클래스 상세는 사용자별 데이터가 없어 `ClassView`가 데이터만 받아 그린다. 화면은 `await connection()` 뒤에 읽는다
- 마감(`closed`)으로 바꾸는 곳이 없다. 운영 화면은 대리 등록과 다가오는 클래스 목록뿐이다
- 강사 로그인 화면(T-03)이 없다. 강사 응답은 운영자가 대신 남겨야 한다

### 기존 패턴

- 추가요(`src/server/requests`, `src/app/song/[slug]/request-panel.tsx`): upsert로 1건 유지, 취소 후 다시 하면 `created_at`을 지금으로, 첫 요청이면 축하 오버레이, 비로그인은 로그인 시트 → `?request=open`으로 돌아와 시트 자동 열기
- 서버 액션은 첫 줄에서 `getCurrentUser()`(수강생) 또는 `requireAdmin()`(운영)으로 다시 확인하고, 끝나면 `refresh()`
- 운영자 클래스 등록은 `createClassByAdmin`(트랜잭션 안에서 장소·곡 확인, 공개면 추가요 열기). 곡 고르기는 `SongPicker`
- 시안 round-3의 앵콜 응원봉: 라일락 카드, 오른쪽 위 응원봉, 게이지(핑크 줄무늬), 누르면 응원봉 흔들림 + 아래에서 관객 응원봉이 올라왔다 내려감 + 숫자 튐 + 작은 색종이 + 진동

## Technical Decisions

| Decision | Rationale |
| -------- | --------- |
| 강사 응답(검토할게요·어려워요·앵콜 클래스 열기)은 운영자가 대신 남긴다 | 강사 화면과 알림이 없다. 운영자가 DM으로 전하고 답을 기록한다(F-24 MVP 전달 방법). 강사 화면이 생기면 같은 서버 함수를 쓴다 |
| 앵콜 라운드 행은 첫 앵콜이 들어올 때 만든다. 기준 인원·만료 시각은 그때 고정 | 마감·종료되는 순간을 잡는 배치가 없다. 앵콜이 없는 클래스는 행도 필요 없다 |
| 만료는 저장하지 않고 읽을 때 계산한다(모으는 중·전달됨이면서 만료 시각이 지났으면 만료) | 배치 없이도 화면과 서버 판단이 같다. 검토 중은 만료되지 않는다(S-4) |
| 기준 도달은 앵콜 저장 트랜잭션 안에서 라운드 행을 잠그고 센다 | 동시에 앵콜이 들어와도 전달됨 전이가 한 번만, 정확히 일어난다(app.md 상태 전이) |
| 다시 앵콜하면 같은 행을 살리고 `created_at`을 지금으로 | 추가요와 같은 규칙. 인원은 유효 행 수로 센다(숫자를 두 곳에 저장하지 않는다) |
| 앵콜 클래스 등록은 원 클래스의 강사로 고정하고, 원 라운드가 전달됨·검토 중일 때만 연결한다 | 앵콜은 같은 강사가 같은 클래스를 다시 여는 것이다. S-4에서 오픈은 전달됨·검토 중에서만 간다 |
| 마감 풀기는 앵콜이 한 번도 없는 클래스만 | 앵콜이 쌓인 뒤 다시 열면 앵콜한 사람의 상태가 사라진다. 실수로 마감한 경우만 되돌린다 |
| 앵콜 취소는 상태와 관계없이 한 번 더 묻는다. 전달됨·검토 중이면 "강사님이 보는 인원에서 빠져요" | design.md "취소는 시트로 한 번 더". 문구는 F-24 그대로 사실만 |
| 응원봉 움직임은 앵콜을 처음 남길 때만, 클래스 상세 안에서 | 감정 순간에만 크게(design.md). 수정·취소는 짧은 안내만 |

## Issues Encountered

### 1. 운영 화면을 운영자 로그인 없이 확인할 수 없다

**문제**:

운영 앵콜 화면, 마감 버튼, 앵콜 클래스 등록 폼은 운영자 로그인이 있어야 열린다. 수강생 앵콜 저장도 카카오 로그인이 필요하다.

**원인**:

로그인과 비밀번호 입력은 사용자가 직접 한다(core-principles).

**해결**:

규칙(상태 전이·기준 도달·만료·마감 풀기·앵콜 클래스 연결)은 서버 함수를 되돌리는 트랜잭션 안에서 실행해 확인했다. 수강생 화면의 상태별 모양은 데이터만 받아 그리는 `ClassView`에 가짜 값을 넣어 확인했다(임시 페이지, 커밋 안 함).

**결과**:

화면 동작(운영 화면, 실제 앵콜 저장과 응원봉)은 사용자 확인

## Learnings

### 서버 함수를 되돌리는 트랜잭션 안에서 돌릴 수 있다 (2026-11-03)

`getDb()`는 연결을 `globalThis`에 하나 둔다. 검증 스크립트에서 바깥 트랜잭션을 열고 그 트랜잭션을 그 자리에 넣으면, 서버 함수 안의 트랜잭션은 저장점(savepoint)이 되어 실제 함수를 그대로 돌리고 마지막에 전부 되돌릴 수 있다. 가짜 사용자(`auth.users`·`profiles`)도 같은 트랜잭션 안에서 만들면 공유 DB에 아무것도 남지 않는다. SQL을 따로 흉내 내는 것보다 실제 코드가 만든 쿼리를 확인한다.
